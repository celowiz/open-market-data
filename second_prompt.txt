## 6. Foundation engineering constraints

Preserve the architectural principles already defined by the project.

### Domain ownership

The project owns its canonical domain model.

Do not expose third-party provider/library models outside their adapters.

### Provider isolation

External data libraries must remain behind provider interfaces/adapters.

No application layer should depend directly on libraries such as:

- `yfinance`
- `PYield`
- `python-bcb`
- `mercados`

unless it is inside the relevant provider adapter.

### Data domains

Preserve the distinction between:

- instrument quotes;
- market-series observations;
- curve points.

Do not collapse everything into one generic quote model.

### Financial values

Use exact decimal types where financial precision matters.

Do not persist financial prices using binary floating-point types.

### Provenance

Foundation models and storage design must make provenance possible.

Important concepts include:

- source;
- raw artifact;
- reference date;
- retrieved timestamp;
- ingestion run;
- revision;
- quality status.

Do not overbuild provenance features that belong to later phases, but do not design Foundation in a way that prevents them.

### Stable identifiers

Canonical public/domain identifiers must not depend solely on ticker or provider-specific symbols.

Instrument identity should remain extensible to multiple external identifiers.

### Idempotency

Design ingestion/storage primitives so future provider ingestion can be idempotent.

Do not implement complicated ingestion logic before it is required.

### Schema drift

Foundation should leave an appropriate extension point for future schema-drift detection.

Do not build provider-specific schema-drift logic yet unless Phase 1 explicitly requires it.

## 8. Secrets and configuration

Never commit secrets.

Never print secrets in logs or final output.

Do not modify `.env` with generated credentials unless explicitly required.

Use `.env.example` to document configuration.

The application should use sensible defaults wherever possible so that local development does not require unnecessary environment variables.

At this stage, avoid adding speculative environment variables that no implemented code consumes.

If `.env.example` contains variables that Foundation does not yet use, preserve them unless there is a clear reason to change them.

## 9. Dependencies

Use `uv` as the Python package/environment manager.

Before adding a dependency:

1. verify that it is actually needed in Phase 1;
2. prefer maintained, conventional libraries;
3. avoid overlapping libraries that solve the same problem;
4. consider licensing;
5. avoid adding future-provider dependencies before their phase unless Foundation genuinely needs them.

Do not install large frameworks for problems that can be solved simply.

Avoid unnecessary architecture such as:

- dependency-injection frameworks;
- microservices;
- Redis;
- Celery;
- Airflow;
- Kafka;
- Kubernetes.

## 10. Database and migrations

If Phase 1 includes PostgreSQL schema creation:

- use SQLAlchemy 2.x conventions;
- use Alembic for migrations;
- keep database models and domain/API models appropriately separated;
- use explicit constraints where they protect important invariants;
- avoid premature partitioning;
- avoid excessive indexes;
- use exact numeric database types for financial values;
- use timezone-aware timestamps where appropriate;
- use UTC for persisted timestamps;
- use date types for financial reference dates when appropriate.

Migrations must be deterministic and reviewable.

Do not create destructive migrations unnecessarily.

If executing migrations against the configured development database, verify the target first and never assume it is disposable.
